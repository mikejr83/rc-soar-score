# Ticket 010 — Recalculation Invalidation Scope

- **Category:** Scoring Engine
- **Priority:** Medium
- **Status:** ready
- **Decision:** A calculation-affecting change to a global contest option (group-score mode, rounding/precision, dropped-round policy, target/working time, pps, F5J height/reference/motor-restart, team-pilot count N, tie-breaker) triggers a **full recalculation of all derived results** and a **new calculation revision**. Precision-only changes always recalc. The landing-table revision is **entry-scoped** (affects only new score entries; already-scored rounds stay frozen under the revision they were scored with) and is therefore **not** a recalc trigger for existing data. Presentational fields (numbering, classes, model tracking, scoring lock, review-request enablement, public update mode) never recalc. Draw fields route to a matrix revision (ticket 003).

"Any calculation-affecting change invalidates derived results and creates a new calculation revision." The boundary between calculation-affecting and presentational changes was not defined. This ticket now pins down (a) which initial config settings are calculation-affecting vs. presentational vs. entry-scoped, (b) that a precision-only change always recalculates, (c) that a landing-table change is entry-scoped and does not recalculate already-scored rounds, and (d) that invalidation is a **full recalculation** (no targeted/dependency scope).

## Context (original)

"Any calculation-affecting change invalidates derived results and creates a new calculation revision." The boundary between calculation-affecting and presentational changes was not defined.
## Questions

1. Which configuration settings are calculation-affecting vs. presentational? — **Resolved: a declarative closed list (see Decisions). No per-field tagging mechanism is required by this ticket.**
2. Does a change to decimal precision alone trigger a full recalc, or only when the rounded values would differ? — **Resolved: always triggers a full recalc + new calculation revision (see Decisions).**
3. Does a change to the landing-bonus table trigger a recalc for already-scored rounds, or only future rounds? — **Resolved: only future rounds; already-scored rounds are frozen under the table revision they were scored with (see Decisions).**
4. When a recalculation is triggered, which derived records are invalidated — all, or only those downstream of the changed setting? — **Resolved: all (full recalculation, see Decisions).**

## Decisions

- **Q4 — Invalidation scope is a full recalculation of all derived results.** Any calculation-affecting change invalidates **every** pilot's `raw score → group score → contest total → dropped-round selection → ranking / team totals` chain (for every already-scored group) and creates **one new calculation revision** that supersedes the prior one. There is **no targeted / dependency-based scope** and no "field → derived-stage" map. Rationale: consistent with the Q1 decision (no dependency mechanism), matches `discipline-scoring.md` rule 1/3 ("mark affected derived values stale … complete affected-scope recalculation" — these *global* settings apply to every group/pilot identically, so "affected" is the full set of derived results), and avoids the silent-stale-result risk that rule 4 forbids. (The one exception, the landing-table revision, is entry-scoped and handled by Q3 — it is not a recalc trigger for existing data.) Superseded calculated values, score state, review history, and audit records are all preserved (per rule 2).
- **Q3 — A landing-table change affects only scores entered after the new revision is selected; already-scored rounds are frozen.** Each score stamps the `table revision used` **at entry time** and stores the resolved points as part of the immutable raw data. Selecting a new landing-table revision applies only to **new** score entries; it does **not** re-resolve the landing bonus on any already-scored round, does **not** update the stored `table revision` on existing scores, and does **not** trigger a recalculation of existing derived results. This makes `disciplines-and-configuration.md`'s "historical scores therefore remain reproducible if a table changes later" literally true: a past round's points are stable because they were computed from the immutable (key + revision) pair.
  - **Consequence for Q1:** "landing-table revision" is **not** a calculation-affecting trigger for *existing* data. It is **entry-scoped** — the table revision in force at the moment a score is accepted. (This is the one field in the Q1 list whose effect is scoped to new entries rather than the whole already-scored contest.) I have moved it accordingly in the Q1 list below.
  - **In-place-edit guard:** Editing the entries of an *existing* table revision in place is not supported. A table change always creates a **new revision**; the in-force revision is then pointed at the new one for future entries. This preserves history and audit.
  - **Typical (expected) flow:** The landing table is **not** normally changed during a contest — the table is tied to the discipline by default. The realistic mid-contest case is a participant noticing a table problem while entering their **first** score; in practice the participant does not self-correct — the contest director selects the correct table. Until a score is entered, there is nothing to re-score.
  - **Regional preference (e.g. Europe distance-based vs. US points-selection):** A director running a region-tailored discipline changes the landing-bonus table (e.g. from distance→points to a points-selection method). The application **tracks this as a discipline/preference change**, not a per-contest scoring edit: the underlying points awarded are effectively the same, and the preference is recorded against the **discipline** and **used for future contests generated from that discipline**. This is a profile/rules-version change, not a per-score or per-contest recalculation trigger.
- **Q2 — A precision-only change always triggers a recalculation + new calculation revision.** A change to rounding/truncation **mode** or to the decimal count is a calculation-affecting change: it triggers a full recalculation (Q4) and a **new calculation revision**, even if the stored full-precision values and the already-rounded numbers are identical. Rationale: uniform revision model — any change to a calc-affecting setting ⇒ a new config revision (per 004) ⇒ a new calc revision; matches Q4's "always recalc" stance; avoids value-comparison logic and the data-dependent "does a new revision exist?" outcome; and preserves the contract that the published total is always derived from the current calc revision whose stored rounding/precision metadata describes exactly what was published. (Precision is *not* treated as presentational.)
- **Q1 — Calculation-affecting vs. presentational is a declarative closed list.** This ticket settles the boundary by **enumerating the initial config fields** as calculation-affecting or presentational. It does **not** require a per-field `calcAffecting` tagging mechanism, nor a dependency graph; future fields are classified when they are added to the discipline profile / contest configuration, not retroactively covered here.
  - **Calculation-affecting (recalc + new calculation revision):** group-score mode (`Raw`/`Normalized`/`Time`); rounding/truncation + decimal precision; dropped-round policy (round N, max 2); target/working time; points per second; F5J height penalties (minor/major rates), F5J reference launch height, and F5J motor-restart / Non-Droppable mode; **team-pilot count N** (affects team totals); **tie-breaker enablement** (affects ranking).
  - **Entry-scoped (not a recalc trigger for existing data):** landing-table revision — the table in force at score-acceptance time; selecting a new revision affects only future entries (see Q3). A change to it does **not** recalculate already-scored rounds.
  - **Presentational (no recalculation):** participant unique-number option; pilot classes; model tracking; scoring lock; review-request enablement; public score-update mode (automatic / at round completion / manual).
  - **Out of scope (not in the config bucket at all):** the draw fields (draw mode, groups per round, team protection, lane mode, `PreliminaryManOnManRounds`) are calculation-affecting but route to a **matrix revision** per ticket 003, not to this ticket's config-option list.
  - *Rationale:* a closed list matches the ticket's literal scope and the `discipline-scoring.md` trigger set (contest option, override, landing table, matrix assignment, rules/calc version). `team-pilot count` and `tie-breaker` are included because they are genuine contest config fields that change a derived value (team total, ranking) even though they sit in the organizational/display area of the config UI.

## Acceptance criteria

- **Calc-affecting list is declarative:** the initial contest-configuration field set is classified exactly as in the Q1 decision (calculation-affecting / entry-scoped / presentational). There is **no** per-field `calcAffecting` tag or dependency-graph requirement. A field not yet classified is classified when it is added to the discipline profile / contest configuration.
- **Full-recalc invalidation (Q4):** Changing any calculation-affecting global setting (group-score mode, rounding/truncation + precision, dropped-round policy, target/working time, pps, F5J height/reference/motor-restart, team-pilot count N, tie-breaker) invalidates every pilot's `raw → group → contest total → dropped-round → ranking / team totals` chain and produces **exactly one** new calculation revision superseding the prior one. There is no targeted/partial scope.
- **Precision-only change (Q2):** Changing rounding/truncation mode or the decimal count alone always triggers a full recalculation and a new calculation revision, even when the resulting values are numerically identical. Precision is **not** treated as presentational.
- **Landing-table change is entry-scoped (Q3):** Selecting a new landing-table revision changes the `table revision used` for **new** score entries only. It does **not** re-resolve the landing bonus of any already-scored round, does **not** update the stored `table revision` on existing scores, and does **not** trigger recalculation of existing derived results. An already-scored round's resolved landing points remain exactly those recorded at its entry time (reproducibility of historical scores).
- **Landing-table in-place edit guard:** The entries of an existing landing-table revision are immutable; a table change always creates a new revision.
- **Recalc preserves history (rule 2):** Every recalculation preserves score state, review history, source metadata, audit records, and all superseded calculated values. The prior calculation revision remains queryable.
- **Public presentation (rule 4):** Public projections, participant results, rankings, and team totals are served **only** from the current successful calculation revision; a stale or in-flight recalculation is marked preliminary and never presented as official.
- **Cross-ticket contracts (not restated here):** concurrency of concurrent config edits is ticket 016; draw-affecting config changes create a matrix revision (ticket 003); the override storage/scope model is ticket 004.
- **Golden fixtures:** at least one fixture per trigger class confirms the new-calc-revision and preserved-history behavior: (a) a global-option change (e.g. pps or group-score mode) recalculates all rounds and bumps the revision; (b) a precision-only change bumps the revision even when values are unchanged; (c) a landing-table swap leaves already-scored rounds' resolved points unchanged while new entries use the new revision.
