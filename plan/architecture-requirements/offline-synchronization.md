# RC Soar Score Architecture - Offline Synchronization

## Purpose and Scope

Offline synchronization keeps an account-backed contest director's local contest data recoverable in the remote system while allowing the contest to be administered without a network connection. It is a backup and collaboration mechanism; it is not the act of publishing results.

An accountless offline contest has no remote backup. It may be uploaded later through the anonymous publishing flow, but it cannot participate in ordinary synchronization until it is claimed by an account.

The contest director owns the contest configuration, flight matrix, and official score data. Participant submissions are valid inputs to the contest and must not be silently discarded when the director's value takes precedence. A person helping the contest director enter or review data on the same installation is a local operator, not a separate official user type. Their actions are performed under the director's authority.

This document uses **score** for the discipline-specific raw components entered for one pilot in one group and round. Normalized scores, totals, rankings, and team scores are derived values.

## Synchronization Requirements

1. Every synchronizable entity must have a stable identifier generated by the client or server, an owning contest, and a revision.
2. Every mutation must record the entity revision it was based on, a unique mutation identifier, the actor, the actor's authority, the source device, and the time it was made. Server time is authoritative for ordering remote changes; client time is retained for audit.
3. The service must apply a mutation at most once, even when it is retried. A successful mutation must be acknowledged by its mutation identifier and resulting revision.
4. The service must provide changes after a caller's synchronization cursor. Cursors and acknowledgements must be durable so a disconnected client can retry without creating duplicates.
5. Synchronization must be incremental. A full contest download and export are required recovery operations, not the normal conflict mechanism.
6. The local application must retain unsent mutations and retry them after connectivity returns. A failed sync must not prevent offline contest administration.
7. A local deletion must create a tombstone until the service acknowledges it. Tombstones must prevent a deleted entity from being recreated by an older change.
8. Sync must be scoped to the contest director's authorized data. Participant email addresses and other private data must follow the privacy rules in the participant requirements.

## Administration Installation

1. Each contest has one active administration installation. This installation is the sole offline authority for contest configuration, matrix changes, official score changes, state transitions, and deletions.
2. The application must discourage administration of the same ongoing contest from multiple offline installations. It must show the installation identity and last synchronization state so the director can identify the active installation.
3. A contest director may install the application on a replacement device, but the replacement must be initialized from a complete export or remote backup and explicitly activated as the contest's administration installation while connected to the service.
4. Activating a replacement installation must revoke the prior installation's ability to submit administrative mutations. The prior installation may remain available for read-only access and export, but its later administrative mutations must be rejected as stale or inactive-device changes.
5. If the prior installation is unavailable, the director must be able to recover the contest from the latest remote backup or export and activate the replacement. Any unsynchronized mutations that existed only on the unavailable installation cannot be recovered by the service.
6. A person assisting the director on the active installation may enter or review scores using the same local application. The application does not provision that person as a separate official account or offline authority. All administrative actions performed on the installation are attributed to the contest director, who remains accountable for them.
7. Activating a replacement installation requires an authenticated session for the contest director's owning account while connected to the service.

## Pull and Push Protocol

At the start of a sync the client sends its last acknowledged cursor and its unsent mutations. The service then:

1. Authenticates the director and verifies access to the contest.
2. Applies non-conflicting mutations in dependency order, or returns a conflict for each mutation that cannot be applied.
3. Returns acknowledged mutations, rejected mutations with a reason and current revision, and all remote changes after the cursor.
4. The client applies remote changes only after preserving its unsent local mutations and audit history.
5. The client advances its cursor only after the returned changes are durably stored locally.

The operation must be safe to repeat after a timeout. A conflict must be visible to the director when it requires a decision; it must not be resolved by last-write-wins timestamps.

## Authority and Conflict Resolution

The service must evaluate a mutation against its base revision. If the base revision is current, the mutation is accepted. If it is stale, the service must classify the mutation as an automatic merge, a director decision, or an invalid operation.

## Scores and Recalculation

1. A group score must retain its original entered components, current official components, all review proposals, and the revision that produced each value.
2. Calculated values must identify the matrix revision, contest-configuration revision, discipline rules version, and calculation version used to produce them.
3. A configuration change that affects calculation must invalidate and recompute derived values without changing raw components or audit history.
4. A participant submission received while the director is offline must appear as a pending remote input after synchronization. It must not replace an offline official score automatically. If it loses to that score, it becomes a silent review record and follows the contest's configured review policy only if the director separately opens a review.
5. Scores that are locked, or belong to a contest state that disallows modification, must be rejected with an actionable explanation. A review request cannot modify a locked score.

## Deletion and Publication

1. Deletions synchronize as tombstones and require authorization. An offline deletion must be shown to the director before it removes remote data. Tombstones, rejected submissions, conflict records, and score audit history are retained for the lifetime of the contest.
2. Deleting a contest that was published at least once deletes only the director's data. The published record remains, loses only its link to the contest, and can no longer be updated. Removing it from public view requires a delist request that a system administrator decides.
3. If a contest is deleted, its contest data, tombstones, rejected submissions, conflict records, and score audit history are deleted as well.
4. Publishing is an explicit operation separate from backup synchronization. A publish request identifies the private contest revision being published and creates a versioned public projection.
5. A later publish updates the public projection only after the service validates the contest revision, state, visibility, and privacy rules. A failed publish must not alter the private contest.
6. Anonymous publishing does not create remote backup data. Claiming the contest with the verified publishing email may establish an account owner according to the account requirements.

## User Experience and Recovery

The application must show the last successful sync, pending mutations, conflicts requiring action, and the remote contest revision. The director must be able to inspect both versions, choose the winning value where permitted, and retry or discard a failed mutation without losing local data. The application must clearly warn that changes made after the last successful synchronization cannot be recovered if the installation is lost.

The service and application must support exporting a complete local contest, including raw score data, revisions, audit history, tombstones, and pending mutations. Importing an export must preserve identifiers and must not silently overwrite an existing contest.
