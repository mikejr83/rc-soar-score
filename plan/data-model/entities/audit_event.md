# Audit Event

**Relationship to architecture-requirements:** plan/architecture-requirements/data/synchronization-and-audit.md  
**Purpose:** Immutable change log recording every mutation, state transition, score attempt, and conflict in the system. Sensitive credentials and private message contents are excluded.  
**Identifier:** `id` (UUIDv7)  
**Parent entity:** None  
**Child entities:** None

## Relationships

- Logs changes to any entity type through `entity_type` and `entity_id`
- Belongs to a Contest (`contest_id`), a director's data (`owner_account_id`), or a publication (`publication_id`), or to none of them for events outside any contest
- Made by an Account (`actor_id`) from an Installation (`installation_id`)
- Immutable and append-only: once created, events are never modified or deleted

## Invariants and Constraints

- Audit events are immutable once created and append-only; none are modified or deleted
- At most one of `contest_id`, `owner_account_id`, and `publication_id` identifies the scope. A publication event after contest deletion has only `publication_id`
- Client time is retained only as audit information. It is not compared with server time, because client clocks drift
- Sensitive credentials and private message contents are excluded. Redaction events identify the row by `pilot_key` and never contain the redacted details
- `base_revision` and `resulting_revision` capture the optimistic locking state
- A `StateTransition` event of a contest director action records the action and the old and new value in `reason`, as `lock: AdminLock Unlocked → Locked` (the action name, a colon, then each changed field as `Field Old → New`, separated by `; `). The entity has no separate fields for them. `ContestTransitionAudit` in `soar_score_core` writes and reads this text
- A `ConfigurationSaved` event has entity type `ContestConfigurationRevision` and the revision's id as `entity_id`. `base_revision` is the previous configuration revision number (null for the first save) and `resulting_revision` the new one. A `MatrixDrawn` event, written for a first draw, an extension and a redraw alike, has entity type `MatrixRevision`, the matrix revision's id as `entity_id`, the previous and new matrix revision numbers in `base_revision` and `resulting_revision`, and the revision's reason (`initial draw`, `rounds added`, `redraw from round 3`) in `reason`. Both are stored in the same transaction as the change; a refused save or draw leaves none
- A `ScoreAttempt` event records a director's correction of an official score (entering a score for a slot that already has one); a first entry leaves none, so the trail stays readable. It has entity type `ScoreAttempt` and the correcting attempt's id as `entity_id`; `base_revision` and `resulting_revision` are the old and new score revisions. The pilot, round and old and new points travel in `reason` as `correction: pilot 12; round 3; group 2; points 82.4 → 95.1; reason: Timer misread` (the pilot by participant number, not by name). `ScoreCorrectionAudit` in `soar_score_core` writes and reads this text. A pilot's retirement or reinstatement is a `StateTransition` event on the `ContestParticipation` with `reason` `retire: pilot 12; from round 3` (`from round 2 → 4` when the round moves) or `reinstate: pilot 12; was retired from round 3`; `PilotRetirementAudit` writes and reads it, and only a changed retirement round leaves one. Both are stored in the same transaction as the change; a refused correction leaves none

## Lifecycle

N/A (immutable)

## Privacy and Scope

- Contest and director events are shared with the owning director's installations through synchronization. Participants never receive them
- Events include installation and device identifiers for traceability
- Private fields from the changed entity are not included in audit events

## Audit and Synchronization

- Audit events are themselves synchronized to the director's installations so they hold the full audit trail for their scope
- Events are generated on the client for immediate display and by the service for authoritative ordering
- A change that conflicts with a concurrent change produces an event with outcome `Conflict`
