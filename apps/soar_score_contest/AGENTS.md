# Contest App Agent Guide

Contest management application for directors, pilots, and helpers. Runs on web and Windows (embedded offline).

## Structure

- `lib/main.dart` — entry point
- `lib/features/` — page widgets by domain: contests, pilots, score-entry, results
- `lib/server/` — Windows-only embedded offline server logic
- `lib/widgets/` — local reusable widgets (not shared with public app)

## Boundaries

- **Must not do direct database access**. All data access goes through `soar_score_api` client (which talks to `soar_score_api_handlers`, which uses `soar_score_data` backed by SQLite in the native app or by PostgreSQL on the server; the web build has no local database and calls the remote API).
- Depends on: `soar_score_core`, `soar_score_data`, `soar_score_api`, `soar_score_sync`, `soar_score_ui`, `soar_score_ui_storage`
- UI-only state (theme, hidden panels, drafts) goes through `LocalUiStore` from `soar_score_ui_storage`, reached with `localUiStoreOf(context)` (`lib/local_ui_store_provider.dart`; `null` in bare-page tests). Key every call by account id. Contest data never goes through it.
- The New Contest draft is kept per account through `ContestDraftStore.persistence` (`LocalUiDraftPersistence`, key `new_contest_draft`). `ContestDraftCodec.version` is the stored shape: raise it when a draft field changes incompatibly, and older drafts are then offered for discard. Add any new `ContestDraft` field to the codec and its round-trip test.
- Closing the tab or window: a page with unsaved edits attaches to its `UnsavedChangesGuard` with `attach(confirm, hasChanges: ...)`; `hasChanges` must be synchronous and cheap. `installCloseWarning()` (`lib/services/window/close_warning.dart`, called from `main`) then arms the browser's `beforeunload` (web, generic browser prompt) and, on desktop, an `AppLifecycleListener.onExitRequested` that asks every attached page via `UnsavedChangesGuard.confirmCloseAll()`. Pages read `UnsavedChangesGuard.closingApp` to word their dialog for a close ("Close RC Soar Score?"). Do not add per-page hooks. Windows sign-out and shutdown are not covered.
- Page states: a page that loads, is empty, cannot be reached, is not allowed or has a conflict shows `PageStateView` (`lib/widgets/page_states/page_states.dart`); a problem above still-usable content is a `PageBanner` (title, text, child, any number of `PageBannerAction`s, `band` or `card` shape; a page's own banner such as `ConfigBanner`, `MatrixBanner` or `WizardBanner` only wraps it with that page's copy and never draws its own layout); a status value gets a `StatusLabel` so it is spoken as "Field: value". Sort an API error with `ApiFailure.of(error)` (`lib/services/api_failure.dart`) instead of matching status codes in the page; it reads the server's `code` first. A load that fails goes through `loadFailedView(error, title:, onRetry:)`, which offers Retry only when `ApiFailure.retryable`. A save that fails shows `SaveFailedBanner` (the form keeps every value; Retry only for retryable failures; Dismiss only closes it); the landing editor creates with one id for its whole life so a Retry cannot duplicate. The participant editor has its own failure handling (`ParticipantEditorController`, `EditorBanner`). Use `confirmDiscard(context, ...)` for the discard question and pass your own copy when the page has something specific to say (configuration and the wizard do). Every load state (home, managers, configuration, matrix, scoring, participant editor) goes through these; `MessageView` is gone.
- Visible text goes through `AppLocalizations` (`lib/l10n/`, ARB files, ADR 0004): add each new string to `lib/l10n/app_en.arb` with a `description`, run `flutter gen-l10n` and commit the generated files, and read it with `AppLocalizations.of(context)`. The Settings page is migrated; other pages still hold their text inline and move over feature by feature (a screen's text stays inline until its widgets are migrated, so do not mix). Exception: a new widget file, or a widget rewritten substantially, uses ARB from the start. The ARB files are moving to a shared package for all apps (#558); the bulk migration is #493 (M5). In tests read expected text from `AppLocalizationsEn()`. Translators work from `docs/translating.md` and `tool/l10n.dart`.
- `soar_score_sync` is imported only by `lib/platform/native_sync.dart` and `native_bootstrap.dart`, so the web build contains no sync engine (`test/platform/web_closure_test.dart` checks it). Screens reach sync state through `AppBootstrap`, never the package.
- The Material themes and shared color tokens live in `soar_score_ui` (`theme/app_theme.dart`): `ContestAppTheme`, `PublicAppTheme`, `SelfScoreAppTheme`, `AppColors`, `AppStatusColors`.

## Design Notes

- Offline-aware: UI must not assume connectivity (see `plan/architecture-requirements/offline-usage.md`). Show pending-changes state, provide manual sync trigger.
- The web build stores no contest data in the browser (IndexedDB is limited to preferences and front-end functionality). The native build syncs on connect, then writes locally first and immediately through the remote API.
- Routing constructs are shared with `soar_score_self_score` via `soar_score_ui`; the public site is a separate Next.js app (`soar_score_web`).
- Mobile-first responsive layouts (see `plan/architecture-requirements/responsive-design.md`).

## Testing

- Widget tests: `flutter test`
- Integration (E2E) tests: `scripts/e2e.ps1` (or `scripts/e2e.sh`) runs `integration_test/` against the real app on the demo database, recreated per run. Local only, not in CI (`melos test` and CI run `test/` only; keep it that way, the Windows desktop app and a display are not available there). Windows by default; `-d web` (`-Device web` in `e2e.ps1`) runs the same journeys in headless Chrome, which is what cloud agents use (see Web mode below).
  - **Keep them current.** After any change to a page, route, widget key, visible label, flow or the demo data, run `scripts/e2e.ps1` and update the affected journeys in the same change. **UI PRs extend the matching phase file** under `integration_test/journey/` with a step; they do not add a journey file. Shared steps live in `integration_test/support/`. See "The lifecycle journey" and "Standalone files" below.
  - **The lifecycle journey.** Every test file costs a full app launch, so the rule is one launch per file, many steps. `contest_lifecycle_journey_test.dart` runs a contest from the landing page to the results report in six phases (`phase_1_start.dart` to `phase_6_finish.dart`), each a function that registers its steps on a `Journey`.
    - `Journey.phase(n, title, body)` groups steps; `Journey.step(title, body, {nativeOnly, timeout})` numbers, times and logs a step and, on failure, reports the step, route and screen texts. A step that exceeds its timeout (4 minutes by default) is reported as hung, but its body is not cancelled. `nativeOnly` skips a step on web.
    - `JourneyContext` (`journey/journey.dart`) holds the shared data: the contest name (`E2E Open 2026`), the roster, the pilot names, `groupsPerRound` and `rounds`. Steps read names and counts from it instead of hard-coding them, and never depend on matrix-draw results (scoring steps use `flightOf`, derived from the pilot's place in `pilotNames`).
    - `E2E_STOP_AFTER=<phase number>` ends a run after that phase, so a change to an early phase can be checked without the full run.
    - **Steps re-anchor.** Each step starts from a known place (`goToMainPage`, `openContest`, `openRoundGroup`) and never relies on where the previous step left the screen; it uses its own data. A failed step then points at itself, not at its neighbour.
    - Per-file timeout (web runs only): 1800 s for the lifecycle file (about 13 minutes on web), 300 s for the others; `E2E_TEST_TIMEOUT` overrides it for every file.
    - On web the steps are also posted to the E2E server (`POST /__e2e/log`) and echoed live as `[E2E]` lines by `scripts/e2e.sh`; `-- --dart-define=E2E_SCREENSHOTS=steps` saves a screenshot after each step in `build/e2e-screenshots/`. `bool.fromEnvironment` reads a define on the web only in a `const` expression (otherwise it answers false), so keep every define in a `const` field.
    - Scoring steps (phases 5-6, `journey/scoring_steps.dart`): find a pilot's row with `rowOf`/`openGroupOf` and confirm a save by the strip's official count, because a list builds only the rows near the screen. The web app does not know which account it acts as, so the lock note reads "locked at ..." there and "locked by you at ..." on Windows.
    - Native-only code (`dart:io`, the embedded server) stays behind a conditional export (`if (dart.library.js_interop)`), as in `journey/export_step.dart`, so the web build compiles.
  - **Standalone files.** Only a feature outside the lifecycle, or one that needs its own launch, gets a standalone `*_test.dart`, with a one-line reason in the PR. The allowed files and why:
    - `signed_out_landing_journey_test.dart`: the signed-out start, before any session exists.
    - `close_warning_test.dart`, `save_failure_retry_test.dart`: need the app to be closed or a server write to fail, which would break the lifecycle run.
    - `new_contest_wizard_draft_test.dart`, `new_contest_wizard_fresh_draft_test.dart`, `new_contest_wizard_resume_draft_test.dart`: draft handling across launches.
    - `preferences_setting_test.dart`, `theme_setting_test.dart`, `text_size_setting_test.dart`, `hidden_areas_test.dart`: local settings that must start from a clean install.
    - `report_printing_test.dart`, `pilot_cards_report_test.dart`: native printing and QR output.
    - `contest_import_inspection_test.dart`, `contest_import_refused_test.dart`: import of prepared files, including refusals.
    - `back_to_back_draw_test.dart`, `matrix_rounds_test.dart`: draw options and adding or redrawing rounds on a ready contest, which change the lifecycle contest's draw.
    - `matrix_draw_cancel_test.dart`: the slow-draw hook (`SOAR_SCORE_E2E_SLOW_DRAW`).
    - `offline_frame_status_test.dart`: native storage and sync indicator.
    Adding to this list needs the reason in the PR and Mike's agreement.
  - One `flutter test` run per file: the Windows app allows a single instance, so a second file cannot launch while the previous app is alive. The scripts handle this; do not run `flutter test integration_test` as a whole.
  - The tests need the demo flags: `--dart-define=SOAR_SCORE_DEMO=true --dart-define=SOAR_SCORE_DEMO_RESET=true`. The scripts pass them. For VS Code, use the `soar_score_contest (E2E, current file)` launch configuration, or for the Testing pane set `dart.flutterTestAdditionalArgs` to those two defines in your own (untracked) `.vscode/settings.json`. Run one file at a time from the pane; running the whole folder fails on the second file for the reason above.
  - Writing journeys: a `ValueKey` on a `Text` or `TextField` is on that widget, so read its `data` or controller instead of `find.descendant(of: key, ...)`. Close any running app instance before a run.
- Web mode: the browser build has no local database and no offline mode, so `-d web` builds the app with `--dart-define=SOAR_SCORE_E2E=true` (`lib/auth/e2e_signed_in_session.dart`, an always-signed-in session that sends no token; ignored in release builds) and points it at `apps/soar_score_server/tool/e2e_server.dart`. That server has no token checks, serves a fresh SQLite database with the system and demo data (every request acts as the Local account, like the Windows embedded server), and allows cross-origin calls. It must never be deployed. `POST /__e2e/fail-next-write` makes its next write answer 503 once (used by `save_failure_retry_test.dart`, which is web-only because the Windows build's embedded server gets no such hook). The scripts start it per test file and run `flutter drive` (`test_driver/integration_test.dart`) with `-d web-server`. Needs Chrome and a matching `chromedriver`: run `scripts/e2e-setup.sh` (or `.ps1`) once to install both into `.e2e-tools/` (git-ignored), where the scripts find them; `CHROMEDRIVER` / `CHROME_EXECUTABLE` override that, and `chromedriver` on PATH is the last resort. **Agents: run the setup script before the first web E2E run.** The scripts fail at once when chromedriver is missing or does not answer, and stop a test file that runs longer than `E2E_TEST_TIMEOUT` seconds (default 300) as failed; a healthy file takes about a minute, so a run that is quiet for longer than that is hung, not slow. The web E2E build opens report viewers in place (`InPlaceReportLauncher`, chosen by `ReportLaunchers.current` when `SOAR_SCORE_E2E` is set), because a journey cannot drive a second browser tab, so report content can be checked on web. A contest moves Created -> Configuring (configuration saved) -> Ready (matrix drawn) -> Running (first official score saved); Complete needs Running. `E2E_TEST_TIMEOUT` overrides the per-file limit for every file (web runs only; a Windows run has no timeout); `contest_lifecycle_journey_test.dart` gets 1800 s (others 300 s). Journeys must run on both targets; avoid `dart:io` and native-only screens (Sync) in them, and when a journey is native-only, say so in its file.
- Platform-specific tests: `flutter test integration_test/platform/`
