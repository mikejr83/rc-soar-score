# Scoring Lifecycle

How a score becomes official, for anyone touching the score model, the score routes or sync (requirements: `plan/business-requirements/contest-official-scoring.md`, `plan/architecture-requirements/score-review-and-validity-state.md`):

- **Submission.** A pilot's score (self-scoring or a helper) is a `ScoreAttempt` with participant authority and the slot's placeholder becomes `Submitted` (`ScoresService.submitParticipantScore`). It is preliminary: results and official counts never include it, while "entered" counts do (`RoundProgress.count`). A director's own entry (`enterOfficialScore`, bulk `enterOfficialScores`) writes an attempt and an official version at once.
- **Official versions.** Each official score is a numbered version of the slot (`OfficialScore.scoreRevision`, one more than the revision the writer read; a different stored revision is a `StaleRevisionError`, 409 `stale_revision`). Earlier versions and attempts are kept. A correction needs a reason. Locks at score, group, round or contest level refuse writes (`score_locked`, `contest_locked`). `OfficialScore.selectionOrigin` is `Manual`, `Automatic` or `ReviewDecision`, and `setBy` is null exactly when it is `Automatic`; review stays open for an automatic score until a director confirms it (`ScorePlaceholder.reviewClosedScoreRevision`, `isReviewClosed`).
- **Promotion.** Marking a stored submission official (`promoteSubmission`, `POST .../scores/official`, the group route) adopts exactly that attempt at that score revision and never overwrites a newer one. Naming a submission the contest already accepted automatically is a confirmation: review closes, no second version. On a native installation whose contest syncs (and whose first upload finished) the request is queued as a `promote_score` intent (`PromotionIntentPolicy`) and decided by the service (`plan/architecture-requirements/sync-protocol.md`).
- **The contest score gate.** Every score writer runs inside `officialScoreRepository.withContestGate(contestId, ...)`: one writer per contest at a time (an advisory lock with a 30 s timeout on PostgreSQL). A nested use is a savepoint; a lock timeout or deadlock is `ContestBusyError`, answered 503 `contest_busy` with `retry-after` and nothing kept, so the request is safe to repeat. Accepted sync is outside the gate by design, so evaluations must be retry safe.
- **Automatic officialization.** The option `scores_become_official` (`EndOfRound`, `EndOfGroup`, `Manual`; a missing value reads as Manual, a new wizard contest gets `EndOfRound`) is evaluated on the server by `AutomaticOfficializationService` (`scores_service_automatic.dart`): a round or group is due when every slot nobody is excused from has a score, then its `Submitted` slots become official as the system with a fixed operation id (idempotent), slots with an open review are held, locked scopes are skipped, and `officializeAndRecalculate` recalculates in the same gated transaction. It runs after a participant submission and, through `RecalculationService.automatic`, after director writes, retirement, assignment, team and configuration changes and accepted sync. A failure never fails the caller's change; the server repeats owed evaluations at start (`recoverAutomaticOfficialization`, only for submissions that arrived after a contest's first upload). Imports never run it and a contest's first upload never evaluates (an import's pending scores stay pending), and an installation whose contest syncs never accepts on its own: the service decides and its acceptance arrives as an aggregate in a pull. A new trigger must call `RecalculationService.recalculateAfterEntry` after its change commits. Review decisions (#145) are not built yet; when they are, they must do the same.
- **Who entered it.** `ScoreSlot.officialAttemptAuthority` (JSON `official_attempt_authority`) is the authority of the attempt the current official score adopted: participant, helper, director or system. Selection origin and `setBy` say who made it official, not who first entered the values, so a director who marks a pilot's submission official and one who types the values both read as Manual; this field tells them apart. It is null while there is no official score and missing in older responses.
- **Where else.** Contest app: `services/scoring/` (`ScoringController`) and the Scoring page (see the Page Map). Self-scoring app: preliminary notes per score. Retired pilots: a retired pilot without a score is excused, an existing submission stays eligible.

For contest-app route and UI implementation details, see `contest-app-architecture.md`. For route and source-file lookup across all applications, see `page-map.md`.
