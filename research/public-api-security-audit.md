# Public API security posture

**Baseline** `3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246` from the fetched `origin/master`, reviewed November 12, 2026.

**Assessment.** The hosted server has distinct Auth0 account, participant guest-session, and public publication boundaries. Most director operations check contest ownership, and the self-scoring write path derives the pilot and contest from the session. Two sync write paths fail to apply that boundary to the rows they actually write. Role usage also returns cross-account contest metadata when a shared role is queried. Prioritize the three P1 tickets below. No P0 was identified in this source review.

## Scope and ingress

- **Hosted ingress.** The Dart Shelf server serves the documented API host directly. The public Next.js site also proxies `/api/:path*` to `/:path*` on the configured upstream, so its aliases prepend `/api` to the paths in the catalog. No Next.js application route handlers were found. The embedded Windows and test-only servers are outside the hosted deployment scope. - **Router order.** Common middleware surrounds the router. Health and robots are open. The self-scoring router is mounted before the Auth0-wrapped `/api/v1` router. ## Request traces

| Request family               | Entry and identity                                                                                   | Authorization and data boundary                                                                                                                                                |
| ---------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Public projection reads      | Next.js rewrite or direct ingress → hosted Shelf router → public handler                             | Public publication service checks visibility and shapes the current projection before returning it.                                                                            |
| Account contest routes       | Hosted Shelf router → bearer middleware → Auth0 verifier → account resolver → API route registration | The handler or domain service checks the contest owner and applies the relevant child-resource or lifecycle checks.                                                            |
| Participant routes           | Hosted Shelf router → self-scoring handler → invitation resolution or guest-session middleware       | The invitation service derives the contest and participant from the credential. The score and result services use that scoped identity.                                        |
| Sync and conflict resolution | Auth0 account route → sync handler → acceptor, mutation processor or conflict resolver → Drift store | Installation, contest and conflict ownership are checked before processing. The registered handler tree was the inventory source. The `/api/v1/meta` path mentioned in the handler’s introductory comment has no registration at this baseline. The existing cross-contest slice is useful coverage for foreign contest IDs. The sync findings concern separate child references and final writes, where a valid outer scope alone does not enforce isolation.

## Prioritized hardening tickets

P0 is a critical systemic compromise. P1 covers cross-account authorization failures. P2 covers material defense in depth or an unresolved policy boundary. P3 covers guard consistency. A dash in the catalog means the review identified no endpoint-specific follow-up. Shared controls still apply.

### P1-1 · Authorize the row written by conflict resolution

The conflict lookup checks ownership of the conflict’s scope. The merged branch sends the submitted entity to the data store after applying revision bookkeeping. It does not require the resulting entity ID and scope to match the conflict or reapply the ordinary sync ownership checks. The store decodes and upserts the resulting entity by its own key. This creates a cross-account integrity risk for an authenticated caller with an actionable conflict. Bind the resulting ID, scope and ownership to the original conflict inside the write transaction. Reuse reference checks for both accepted competing data and merged data. Acceptance criteria should cover refusal with no row, conflict, audit or sequence side effects, alongside successful in-scope resolutions. [Conflict ownership check](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_core/lib/services/sync/conflict_resolver.dart#L42) · [Conflict resolution write](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_core/lib/services/sync/conflict_resolver.dart#L217) · [Data store upsert](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_data/lib/sync/drift_sync_acceptor_store.dart#L158)

### P1-2 · Enforce referenced-object scope on sync mutations

The exchange authorizes the installation and request scope. The mutation processor checks the submitted and stored primary entity, but the matrix supersession branch looks up and updates the source assignment globally. The SQL update and deferred foreign key constrain identity without requiring that both rows belong to the same contest. A foreign assignment could be marked superseded and omitted from live assignment reads. Score reference checks also establish existence without consistently requiring the same contest and score-slot relationship. Some collision branches include the referenced accepted row in a conflict record, so review those branches for cross-scope disclosure before storing or returning conflict details. Enforce scope on each referenced object before reading its details, emitting a conflict or writing a row. Bind the update predicate to the authorized contest as defense in depth. Test rejection for cross-contest references and unchanged foreign state. [Exchange authorization](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_core/lib/services/sync/sync_acceptor_service.dart#L105) · [Matrix mutation](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_core/lib/services/sync/mutation_processor.dart#L349) · [Score references](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_core/lib/services/sync/mutation_processor.dart#L699) · [Supersession SQL](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_data/lib/sync/drift_sync_acceptor_store.dart#L208) · [Live assignments](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_data/lib/repositories/matrix_assignment_repository.dart#L35)

### P1-3 · Restrict role usage to caller-owned contests

The role-usage service verifies role visibility, then loads participations for that role and returns every matching contest’s ID, name and participant count. System roles are shared, so the role gate does not authorize those contest records. Apply contest ownership to the query or filter before aggregation. Cover a shared role used by two accounts and require each account’s response to contain only its own contests. [Usage handler](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_api_handlers/lib/handlers/roles_handlers.dart#L70) · [Usage aggregation](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_core/lib/services/roles_service.dart#L107)

### P2-1 · Apply consistent invitation-redemption throttling

Redemption counts invitation failures in process using the Fly client address. Body parsing occurs outside the counted failure branch, and counters are per machine and lost on restart. Verify trusted client attribution on both ingress paths and add shared or edge limits that cover malformed requests and repeated valid redemptions as well as failed credential checks. Preserve the uniform invalid-link response. [Redemption and client attribution](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_api_handlers/lib/handlers/participant_handlers.dart#L77) · [Limiter](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_api_handlers/lib/middleware/failure_rate_limiter.dart#L1)

### P2-2 · Make leaked guest access revocable

Session end removes the browser cookie. Invitation issuance can return the same reusable link, and a valid session can retrieve that link. The service checks invitation validity on each request, but director-facing regeneration and revocation are not implemented in this baseline. Add owner-authorized invitation revocation and rotation, and define whether logout should invalidate the current session server-side. Explicitly require a trusted browser origin for credentialed cookie writes in hosted mode and verify no-store and credential redaction at both ingress paths. Keep native bearer requests supported. [Session end](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_api_handlers/lib/handlers/participant_handlers.dart#L212) · [Link retrieval](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_api_handlers/lib/handlers/participant_handlers.dart#L124) · [Cookie-write policy](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_api_handlers/lib/auth/guest_session_auth.dart#L70) · [Invitation lifecycle](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_core/lib/services/invitations/invitation_service.dart#L29)

### P2-3 · Bound request and computation costs

The shared JSON reader buffers the body without a code-level byte cap. The application has no common per-caller rate limit for sync batches, score entry, draws, recalculation or participant results computed on read. Fly’s concurrent request limits help with simultaneous load. Verify ingress request-size enforcement, then enforce limits at the application boundary for body bytes, batch counts, expensive work per account or guest, and execution budgets where needed. Reject oversized input before deserialization or computation. [JSON reader](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_api_handlers/lib/handlers/request_body.dart#L11) · [Common middleware](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_api_handlers/lib/middleware/middleware.dart#L24) · [Participant results calculation](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_api_handlers/lib/handlers/participant_results_views.dart#L14) · [Fly concurrency](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/apps/soar_score_server/fly.toml#L32)

### P2-4 · Verify public projection visibility and caching

Public listings are intentionally cached for 30 seconds. Detail reads enforce visibility and response shaping but do not declare an explicit cache policy. Confirm visibility, redaction and hidden-results semantics at both ingress paths. Give detail responses an explicit cache policy consistent with delisting and redaction, and document the listing’s allowed staleness. Evaluate a uniform response for unknown and non-visible IDs if publication existence is intended to be private. Include projection privacy and cache behavior in regression coverage. [Public routes and caching](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_api_handlers/lib/handlers/public_publication_handlers.dart#L27) · [Projection detail and visibility](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_core/lib/services/publication/public_publication_service.dart#L36)

### P2-5 · Decide how the server proves entitlement to a Local claim

An active account may reserve an unused Local ID. The server checks collisions with accounts and aliases, but the handler submits no installation-bound proof. The service documents that hosted rows under the Local ID do not yet exist, so the observed risk is claim reservation or disruption rather than transfer of existing hosted data. Decide if knowing the Local ID is the intended authority. If it is insufficient, require proof tied to the installation before persisting the alias. [Claim handler](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_api_handlers/lib/handlers/account_claim_handlers.dart#L21) · [Claim rules](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_core/lib/services/account_claims_service.dart#L10)

### P3-1 · Apply ownership checks consistently before expensive request handling

Most contest routes check ownership before parsing the body. Publication writes, activation and conflict resolution defer the equivalent scope check into services after body parsing. Preserve service-level enforcement and use a shared preflight authorization pattern where possible. Keep the distinction between contest ownership and conflict or installation ownership. Build negative coverage for invalid and foreign IDs across both ingress paths and for implicit HEAD on reads. [Common contest guard](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_api_handlers/lib/handlers/contest_authorization.dart#L10) · [Publication registration](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_api_handlers/lib/handlers/publication_handlers.dart#L54) · [Sync registration](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/packages/soar_score_api_handlers/lib/handlers/sync_handlers.dart#L101) · [Existing foreign-contest slice](https://github.com/mikejr83/rc-soar-score/blob/3dd8d38b5028ad70b2ee5b3fc3b1677f92c54246/apps/soar_score_server/test/api_slice/cross_contest_authorization_test.dart#L48)
